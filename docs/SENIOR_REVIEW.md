# Sentinel, reviewed as a senior engineer would review it

If someone handed me this repo and said "make this resume-ready," here's honestly how I'd think about it and where I'd spend my hours. I'm not going to sugarcoat where it stands right now: it's a solid skeleton with real architectural bones, but it currently doesn't run, and a project that doesn't run in a live demo does more damage to a resume than no project at all. Everything below is ordered by what actually moves the needle first.

## The one thing to internalize before anything else

Right now, if an interviewer clicked "Ask Sentinel," they'd get an error. That's not a stretch goal problem, that's a "this line of the story falls apart the moment someone touches it" problem. Senior engineers get judged less on how ambitious their side project is and more on whether the thing they claim works actually works when someone pokes at it. So before we talk about hybrid search or Azure or any of the exciting stuff, the first rule is: nothing gets added until the existing surface area is solid. A broken RAG demo is worse for your credibility than a boring one that works.

## How I'd reframe the story, before touching code

Right now this reads as "I built a RAG chatbot," which is the most oversaturated sentence in every junior-to-mid AI resume in 2026. Every bootcamp grad has a RAG chatbot. What makes this one different is the domain: you pointed it at a real, large, messy open-source codebase (Apache Superset, hundreds of files, Python + TypeScript + docs) instead of a PDF of a company handbook. That's actually a much harder and more realistic problem — enterprise companies don't need "chat with my PDF," they need "help my engineers stop re-discovering the same internal code every six months." That's the pitch. Lead with that framing on the resume and in interviews: "internal engineering knowledge assistant for large, mixed-language codebases," not "RAG chatbot." Same project, completely different perception.

## Technical changes, in the order I'd actually do them

**1. Fix what's broken.** The `/query` endpoint doesn't return anything. The retriever reloads the embedding model on every single call, which makes it painfully slow. There's a dead file with a `NameError` sitting in the repo. The frontend sets an error message it never shows the user. None of this is hard to fix, it's maybe a day of work, but it has to happen first and completely, not partially. This is also, honestly, a decent story in itself in an interview: "here's a bug I found where a route handler assigned a variable and never returned it, and it's the kind of bug that's invisible in code review but instantly obvious under load testing" is a much more senior-sounding anecdote than "I never had bugs."

**2. Swap the LLM.** Right now the answer generation runs on a local 1.5B parameter model with no quantization. I'd kill this as the primary path immediately. A model that small, run unoptimized, produces weak and sometimes incoherent answers, especially for code questions where precision matters. If someone actually tests this live, it'll undercut everything else you built well. Move to an API-based model as the default — Claude Haiku or GPT-4o-mini, cheap, fast, genuinely good at grounded citation-style answers. Keep the local Qwen path in the codebase as a documented fallback, because "I designed this to run fully on-prem for data-sensitive clients, with an API-first path for speed" is a legitimately good architectural talking point for enterprise interviews. Just don't demo on the small local model.

**3. Upgrade retrieval to hybrid.** Pure vector search misses exact matches — function names, variable names, error strings, exact API calls, all the things people actually search for in a codebase. Add a keyword index (BM25) alongside the vector search, merge the two with reciprocal rank fusion, then re-rank the merged results with a cross-encoder before handing the top few to the LLM. This is maybe two or three days of real work, and it's the single highest-leverage change for actual answer quality. It's also an excellent whiteboard-round talking point, because it shows you understand the actual failure mode of vector-only search rather than just having heard the word "RAG."

**4. Fix the chunking.** The current code slices code files by raw line count, which means it regularly cuts a function in half. That's a chunk that can never be retrieved usefully because it's missing context on both ends. Switch to boundary-aware chunking for Python using the `ast` module — split at function and class boundaries instead of arbitrary lines — and size chunks by token count, not line count. This is a smaller effort than it sounds and it's the kind of detail that separates "I called an embedding API" from "I understand what makes retrieval actually work."

**5. Add logging and a small eval set.** This is the part almost nobody's portfolio project has, and it's exactly why it stands out. Log every query with what got retrieved and how long it took. Then write down thirty or forty real questions about the Superset codebase with expected answers, and build a tiny script that checks whether the right source files show up in retrieval and whether the answer is actually grounded in them. You don't need a monitoring platform, you need a folder with a JSON file and a script that prints a score. But being able to say "I measured retrieval hit-rate before and after adding hybrid search, here's the number" is a materially different sentence than "I think it works better now." This is what "MLOps familiarity" actually looks like at the level people are hiring for right now, so don't skip it thinking it needs to be elaborate.

**6. Deploy it somewhere real, on Azure specifically.** The current Dockerfile exposes port 7860, which is the convention for Hugging Face Spaces, not really an enterprise deployment pattern. Given the roles you're targeting are automotive and enterprise Germany, and every relevant posting named Azure specifically, I'd containerize properly and push it to Azure Container Apps or Azure App Service for containers. Two containers is enough — backend and frontend, or backend with the frontend served statically. This turns "here's my GitHub repo" into "here's a live link, try it," which is a different tier of credibility entirely.

**7. Add a CI/CD pipeline.** A GitHub Actions workflow that lints, runs a small test suite against the chunker and retriever, builds the Docker image, and pushes it — three or four stages, nothing exotic. It costs you an afternoon once the Dockerfile is solid, and "showed up explicitly in postings" was one of the stronger signals in your own market research, so this is a very direct return on a small time investment.

**8. Add minimal auth before the deploy goes public.** Once this has a real URL, it needs at least an API key check on everything except the health route. This isn't about building an auth system, it's about not shipping a public inference endpoint that anyone can hammer for free. It's also a "thinks about production, not just prototypes" signal that costs almost nothing to add.

**9. Fix the frontend properly, then consider streaming.** Render the error state, pull the API URL from an environment variable instead of hardcoding it, delete the leftover console.log. That's the baseline. If you upgrade the backend to an API-based LLM, adding a streaming response so text appears as it's generated is genuinely worth the extra effort, because it's the single most visually impressive thing in a live screen-share demo, and it's not that much additional code once the backend supports it.

**10. Kubernetes and workflow automation, only after everything above works.** A single local minikube deployment of the already-Dockerized backend is enough to honestly say you've touched Kubernetes, don't go further than that right now. Same logic for n8n: once there's a working upload endpoint, wiring an n8n workflow to hit it costs you almost nothing and lets you tick that box. Both of these are half-day tasks that only make sense to do after the core product actually works — doing them first would be optimizing furniture placement in a house that doesn't have a roof yet.

**11. PyTorch, as an optional stretch, tied into the project instead of bolted on.** If you want a PyTorch rep to actually live inside Sentinel rather than being a separate throwaway exercise, the natural fit is a small trained classifier that routes a query as "about code" versus "about documentation" before retrieval, so the system can weight the search differently. That's a real, if small, training loop — actual PyTorch, not just inference through a wrapper library — and it plugs into the retrieval layer as a legitimate feature rather than an exercise you did in isolation. I'd treat this as optional and do it last, after the core pipeline is solid, since it's not what's going to make or break the story.

## The non-technical work, which matters just as much

A great pipeline nobody can see is worth less than a decent one presented well. Write a clean README with an actual architecture diagram, not just a wall of text — a simple boxes-and-arrows picture of ingestion → chunking → embedding → retrieval → generation goes a long way, and you already have the content for it in your own planning doc. Record a two-minute demo video or GIF for the README, because not every recruiter or hiring manager is going to clone your repo and run it locally, but almost all of them will watch a short clip. Put real numbers on it once you've built the eval set — retrieval accuracy, average response latency, whatever you measured — because specific numbers read as engineering rigor and vague claims read as marketing. And if you want the extra credibility bump, a short write-up of the technical decisions, why hybrid search, why you moved off the local model, what the AST chunking fixed, posted somewhere public, does more for how you're perceived in an interview than another line on a resume ever will.

## Where I would deliberately not spend more time

Don't build a full production auth system, don't stand up a real Kubernetes cluster, don't build a real-time monitoring dashboard, and don't try to make the local LLM path fast and polished. All of those are real engineering problems, but they're not the problems that are being evaluated for the roles you're targeting at this stage, and time spent gold-plating any of them is time not spent making the core RAG pipeline good and demonstrably measured. The market signal you already gathered backs this up directly — Kubernetes and workflow automation were the two lowest-signal items on your own list, so treat them as exactly that.

## If I had to order the whole thing on a calendar

Week one: fix every existing bug, nothing else, until `/query` reliably returns a good answer end to end. Week two: hybrid retrieval plus AST-aware chunking, since these are the two changes that actually make the answers better. Week three: swap in the API-based LLM, add logging and the eval script, and get a real number on retrieval quality. Week four: containerize both sides properly, deploy to Azure, wire up GitHub Actions, add the API key check. Anything past that — Kubernetes, n8n, the PyTorch routing classifier — is bonus round, only worth touching once the four weeks above are done and the project has a live link you'd actually be comfortable sharing in an interview.
