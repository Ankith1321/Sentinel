Sentinel

An internal engineering assistant that answers questions about a large codebase and cites the exact files each answer came from. Currently pointed at Apache Superset.

A user asks a question. Sentinel finds the relevant source chunks, hands only those to an LLM, and returns an answer with citations. It works end to end and is measured: the right file now lands in the top 5 results 67.5% of the time, up from 40%.

Product requirements

Help engineers get a grounded answer without interrupting a teammate.

A confident wrong answer about how code behaves is worse than no answer, because people build bugs on it. So every answer must be backed by retrieved source and cite it.

Primary user

Onboarding engineer

Joined in the last 0–3 months and is about to own code they haven't read. Needs orientation without using up a senior's time.

Secondary user

Cross-cutting engineer

Experienced, but a change touches modules outside their usual area. Needs to understand an unfamiliar path fast.

Not for: customers or non-engineers asking product questions, general-purpose chat, code generation, or multi-tenant SaaS. One organization's codebase per deployment.

"I ask how the chart caching layer works and get an answer citing the actual files, not a plausible guess."

Story 2

"I re-run ingestion after a code change and the index reflects it without doubling every chunk."

Story 3

"As a reviewer, I open the deployed link and get a working, cited answer on the first try, every time."

Risk: local model quality

The small local model may miss the groundedness bar even with an eval set. That, not just speed, is why Phase 5 swaps in an API model.

Risk: building before measuring

Better chunking or hybrid search can't be proven to help without the eval baseline. Hence Phase 1.5.

Constraints and open risks

  • Two runtimes: a CUDA dev machine and CPU-only containers. Test model-loading changes on both.
  • ChromaDB has no horizontal scaling.
  • Docker images and CI are written but have not been built or run yet.
  • The real Anthropic API path has not been exercised without a key.

Rules for any new screen

Stay in palette

Zinc, white, red. Update this brief before adding any new color.

Reuse the card

rounded-2xl, zinc-900 fill, zinc-800 border. No new container style per screen.

States persist

Loading and error are rendered states, not toasts. A 60-second wait makes a vanishing toast read as broken.

Known defect: the loading caption is a <p> nested inside the <button>, which is invalid HTML. Move it out. The textarea staying editable while loading is a deliberate exception to rule 8.7, so users can draft the next question; the submit button blocks double-sends.

Re-indexing rule. When a file changes, delete all its old chunks from Chroma by source_id first, then upsert the new ones. Upsert alone only overwrites ids that still exist, so a file shrinking from 10 chunks to 6 would leave chunks 7–10 in the index serving stale content. Do the same for removed or renamed files.

Deliberately not built

  • No users table. Auth is an API key, not accounts.
  • No full-text-search table. BM25 runs in-process until that's a measured bottleneck.
  • No chunks table. Delete by source_id filter in Chroma instead.

Identity vs. change

documents.id is derived from the path, so it stays stable across runs. content_hash (SHA-256) is what says whether the file changed. This replaces today's fresh-UUID-per-run bug.
